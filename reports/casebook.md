# Performance casebook

The slowest statements of the TopFlow API workload, each with its plan before and after
the fix. The casebook first held 10 cases, chosen by shared buffers touched in
the functional ranking at SCALE=1000000; the measured run at SCALE=10000000 then ranked
the workload by median time (`reports/workload.md`, docs/benchmarking.md).
It added case 11, which the buffer ranking missed.
Cases 8, 9 and 10 fell outside the ten slowest statements and stay; each section says how its case was chosen.
A list endpoint runs its pagination total with its page and the same filter, so a total
that is among the heaviest statements is fixed in its page's case. Plans come from
`EXPLAIN (ANALYZE, BUFFERS)`; CI checks the plan shape of every case (indexes used, nodes
present) and that a rewritten statement returns the same rows, never timings.

- Generated by `./lab casebook --measure` on 2026-10-02 17:41 UTC.
- Data: SCALE=10000000 (about 10,000,000 order lines), history anchored at 2026-10-02 16:00:00.
- Server: PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2).
- Environment: Docker Desktop (Docker 29.8.1), 16 CPUs and 7.4 GiB of memory for all containers on Windows 11 build 26200 (Git Bash); memory limits pg1 3g, pg2 3g, runner 512m; shared_buffers 1GB, effective_cache_size 2GB, maintenance_work_mem 512MB, work_mem 16MB; ASUS TUF Gaming A15 FA507RC laptop (AMD Ryzen 7 6800H, 8 cores and 16 threads; 16 GB of RAM; Intel SSDPEKNU512GZ 512 GB NVMe SSD) on mains power with the Performance power plan, through Docker Desktop's WSL 2 virtual machine; what else ran on the machine during the measured run is recorded in docs/benchmarking.md.
- Timings: median of 15 runs after one warm-up run; server-side planning plus execution time, including converting the rows to text, from EXPLAIN (ANALYZE, SERIALIZE TEXT, TIMING OFF, SUMMARY ON); sending them to the client is not included.

## 1. Audit trail filtered by action prefix, number of entries

- API: `apps/api/src/audit/audit.controller.ts:43 AuditController.list(action startsWith) -> auditLog.count` (workload id `audit-by-action-count`)
- Fix: B-tree index with `text_pattern_ops` for prefix `LIKE`
- Chosen by: shared buffers at SCALE=1000000, and among the ten slowest statements by median time in the measured run at SCALE=10000000 (`reports/workload.md`)
- Parameters: `prefix` = `procurement.quotation\_approval%`

### Why it is slow

The audit screen filters by the start of the action name (Prisma `startsWith`, which becomes
`action LIKE 'prefix%'`) and shows the total for pagination. Nothing indexes `action`, so the
count reads the whole of `audit_logs`, JSON details included, to return one number. A plain
B-tree on `action` would not help either: the database collation is `en_US.utf8`, and
`LIKE 'prefix%'` can only use an index whose order is byte-wise.

### Before

```sql
SELECT count(*)
FROM audit_logs AS a
WHERE a.action LIKE  E'procurement.quotation\\_approval%'
```

```text

  Buffers: shared hit=127833 read=208355
  ->  Gather  (cost=389389.38..389389.59 rows=2 width=8) (actual rows=3.00 loops=1)
        Workers Planned: 2
        Workers Launched: 2
        Buffers: shared hit=127833 read=208355
```

### Trade-off

The prefix becomes a range condition on the new index and the count is answered from the
index alone. The cost is one more index on the table with the most inserts: every audit entry
now updates four indexes instead of three (see `docs/indexing.md` for the measured size and
WAL). `text_pattern_ops` serves `LIKE 'prefix%'` and equality but not `ORDER BY action` or
range comparisons under the database collation; the audit screen needs neither. Prisma cannot
declare operator classes on B-tree indexes, so this index lives in a raw SQL migration.

## 2. Audit trail of one user, number of entries

- API: `apps/api/src/audit/audit.controller.ts:43 AuditController.list(userId) -> auditLog.count` (workload id `audit-by-user-count`)
- Fix: Composite B-tree index (the one added in case 3)
- Chosen by: shared buffers at SCALE=1000000, and among the ten slowest statements by median time in the measured run at SCALE=10000000 (`reports/workload.md`)
- Parameters: `user_id` = `8420f48c-9de4-9e79-03dd-d2bfc4e8dee2`

### Why it is slow

Counting one user's audit entries has no index to use, so PostgreSQL reads every row of
`audit_logs` in parallel and keeps a few dozen. The page query of the same screen (case 3) has
the same missing index.

`("userId", "createdAt")` over an index on `userId` alone.

## 3. Audit trail of one user (first page)

- API: `apps/api/src/audit/audit.controller.ts:35 AuditController.list(userId) -> auditLog.findMany` (workload id `audit-by-user`)
- Fix: Composite B-tree index `(userId, createdAt)`
- Chosen by: shared buffers at SCALE=1000000, and among the ten slowest statements by median time in the measured run at SCALE=10000000 (`reports/workload.md`)
- Parameters: `user_id` = `8420f48c-9de4-9e79-03dd-d2bfc4e8dee2`

### Why it is slow

The planner walks `audit_logs_createdAt_idx` backwards, newest entry first, and throws away
every entry of other users until it has found 20 for this one. For a user with few entries
that means visiting most of the index and fetching a heap row for each entry just to read its
`userId`. The estimate assumes matching rows are spread evenly, which is why this plan looks
cheap to the planner.

### Before

```sql
SELECT a.*
FROM audit_logs AS a
WHERE a."userId" = '8420f48c-9de4-9e79-03dd-d2bfc4e8dee2'
ORDER BY a."createdAt" DESC
LIMIT 20 OFFSET 0
```

```text
Limit  (cost=1000.46..77172.15 rows=20 width=248) (actual rows=20.00 loops=1)
  Buffers: shared hit=31061 read=154849
  ->  Gather Merge  (cost=1000.46..469456.37 rows=123 width=248) (actual rows=20.00 loops=1)
        Workers Planned: 2
        Workers Launched: 2
        Buffers: shared hit=31061 read=154849
        ->  Parallel Index Scan Backward using "audit_logs_createdAt_idx" on audit_logs a  (cost=0.43..468442.15 rows=51 width=248) (actual rows=14.00 loops=3)
              Filter: ("userId" = '8420f48c-9de4-9e79-03dd-d2bfc4e8dee2'::text)
              Rows Removed by Filter: 1528398
              Index Searches: 1
```

| --- | ---: | ---: |
| Shared buffers | 186,024 (1 GB) | 24 (192 kB) |
| Rows returned | 20 | 20 |

- Before (passed): uses index `audit_logs_createdAt_idx`.
- After (passed): uses index `audit_logs_userId_createdAt_idx`; has no Sort node; no sequential scan on `audit_logs`.

### Trade-off

With `userId` first and `createdAt` second, the user's entries are already in time order in
the index: a backward scan returns the newest 20 and stops. A B-tree can be scanned in both
directions, so `createdAt DESC` in the index definition is unnecessary. The index follows
Prisma's naming (`@@index([userId, createdAt])` produces the same name), so it can move into
`schema.prisma` unchanged. Write cost: one more index on `audit_logs`, measured in
`docs/indexing.md`.

## 4. Back-office order search (order, PO or project number, customer or company name)

- API: `apps/api/src/orders/orders.service.ts:660 OrdersService.filters(search) via adminList()` (workload id `orders-admin-search`)
- Fix: `pg_trgm` GIN indexes and a rewrite of the OR across relations into a UNION
- Chosen by: shared buffers at SCALE=1000000, and among the ten slowest statements by median time in the measured run at SCALE=10000000 (`reports/workload.md`)
- Parameters: `pattern` = `%2024-0000%`

### Why it is slow

`ILIKE '%term%'` has a wildcard at the start, so no B-tree index can help: every order is read
and five patterns are tested on each. The customer-name and company-name conditions are
`IN (subquery)` inside the same OR, which forces a filter on each order row rather than an
index lookup. Adding indexes alone does not change that: as long as the OR mixes columns of
`orders` with conditions on other tables, the planner has to scan `orders`.

```sql
FROM orders AS o
WHERE o."orderNumber" ILIKE '%2024-0000%'
   OR o."purchaseOrderNumber" ILIKE '%2024-0000%'
   OR o."projectReference" ILIKE '%2024-0000%'
   OR o."userId" IN (SELECT u.id FROM users AS u WHERE u."fullName" ILIKE '%2024-0000%')
   OR o."organizationId" IN (SELECT g.id FROM organizations AS g WHERE g.name ILIKE '%2024-0000%')
ORDER BY o."createdAt" DESC
LIMIT 20 OFFSET 0
```

## 11. Sales search over quote requests (number, project, company, contact)

- API: `apps/api/src/procurement/rfq.service.ts:508 RfqService.filters(search) via adminList()` (workload id `rfq-admin-search`)
- Fix: One multicolumn `pg_trgm` GIN index over five columns and a UNION rewrite, with case 4's index on organisation names
- Chosen by: median time in the measured run at SCALE=10000000, which placed it among the ten slowest statements although it reads fewer buffers than the cases chosen by buffers (`reports/workload.md`)

### Why it is slow

The sales team's search tests six `ILIKE '%term%'` conditions: the RFQ number, the project
reference, the website visitor's name, e-mail address and company, and the name of the
organisation that sent the request. A leading wildcard rules out B-tree indexes, and the
organisation name is an `IN (subquery)` inside the same OR, so the plan reads every quote
request and tests the patterns row by row. At SCALE=1000000 it ranked 13th by buffers, below
every case chosen that way, but it spends its time on the pattern tests rather than on reading
pages, which is why only the measured run ranked it among the ten slowest statements.

### Trade-off

A GIN index can hold several columns, and unlike a B-tree it serves a condition on any of them
equally well, so one index answers all five patterns on `quote_requests`: the plan combines
five bitmap scans of the same index in a BitmapOr and rechecks the candidates against the real
patterns. Organisation names use the trigram index that case 4 adds to `organizations`, and
the matching organisations' requests come through TopFlow's `(organizationId, status)` index.
As in case 4, the rewrite gives the organisation branch its own UNION arm; with the index
alone the OR still mixes tables and the plan keeps scanning every request. The pagination
total takes the same rewrite.

Costs. One index instead of five, but not five times smaller: every trigram of every searched
column is still an entry, so each new or edited quote request writes as many index entries as
five separate indexes would (WAL per inserted row in `reports/indexing.md`). Quote requests
are written far less often than they are searched by the sales team, which is the case for
paying it. Prisma cannot express the UNION, so `RfqService.adminList()` would call
`$queryRaw` for searches, for the page and its total. Terms shorter than three characters
produce no trigrams and fall back to a scan, as in case 4.
