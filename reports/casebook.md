with its plan before and after the fix. Plans come from `EXPLAIN (ANALYZE, BUFFERS)`;
CI checks the plan shape of every case (indexes used, nodes present), never timings.

- Generated by `./lab casebook` on 2026-09-26 01:43 UTC.
- Data: SCALE=1000000 (about 1,000,000 order lines), history anchored at 2026-09-26 01:00:00.
- Server: PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2).
- Environment: Docker Desktop (Docker 29.8.0), 16 CPUs and 7.4 GiB of memory for all containers on Windows NT 10.0 build 26200 (Git Bash); pg1 limited to 1g with shared_buffers 256MB; the machine was shared with other parallel builds during this run.

## 1. Audit trail filtered by action prefix, number of entries

- API: `apps/api/src/audit/audit.controller.ts:43 AuditController.list(action startsWith) -> auditLog.count` (workload id `audit-by-action-count`)
- Fix: B-tree index with `text_pattern_ops` for prefix `LIKE`
- Parameters: `prefix` = `procurement.quotation\_approval%`

### Why it is slow

The audit screen filters by the start of the action name (Prisma `startsWith`, which becomes
`action LIKE 'prefix%'`) and shows the total for pagination. Nothing indexes `action`, so the
count reads the whole of `audit_logs`, JSON details included, to return one number. A plain
B-tree on `action` would not help either: the database collation is `en_US.utf8`, and
`LIKE 'prefix%'` can only use an index whose order is byte-wise.

### Before

```sql
SELECT count(*)
FROM audit_logs AS a
WHERE a.action LIKE  E'procurement.quotation\\_approval%'
```

```text
        Workers Launched: 2
```

### Trade-off

The prefix becomes a range condition on the new index and the count is answered from the
index alone. The cost is one more index on the table with the most inserts: every audit entry
now updates four indexes instead of three (see `docs/indexing.md` for the measured size and
WAL). `text_pattern_ops` serves `LIKE 'prefix%'` and equality but not `ORDER BY action` or
range comparisons under the database collation; the audit screen needs neither. Prisma cannot
declare operator classes on B-tree indexes, so this index lives in a raw SQL migration.

## 3. Audit trail of one user (first page)

- API: `apps/api/src/audit/audit.controller.ts:35 AuditController.list(userId) -> auditLog.findMany` (workload id `audit-by-user`)
- Fix: Composite B-tree index `(userId, createdAt)`
- Parameters: `user_id` = `7e2e49b0-2383-4b4f-40c1-d33783391787`

### Why it is slow

The planner walks `audit_logs_createdAt_idx` backwards, newest entry first, and throws away
every entry of other users until it has found 20 for this one. For a user with few entries
that means visiting most of the index and fetching a heap row for each entry just to read its
`userId`. The estimate assumes matching rows are spread evenly, which is why this plan looks
cheap to the planner.

### Before

```sql
SELECT a.*
FROM audit_logs AS a
WHERE a."userId" = '7e2e49b0-2383-4b4f-40c1-d33783391787'
ORDER BY a."createdAt" DESC
LIMIT 20 OFFSET 0
```

```text

  Buffers: shared hit=22642
  ->  Gather Merge  (cost=1000.45..47855.48 rows=79 width=248) (actual rows=20.00 loops=1)
```

the index: a backward scan returns the newest 20 and stops. A B-tree can be scanned in both
directions, so `createdAt DESC` in the index definition is unnecessary. The index follows
Prisma's naming (`@@index([userId, createdAt])` produces the same name), so it can move into
`schema.prisma` unchanged. Write cost: one more index on `audit_logs`, measured in
`docs/indexing.md`.

## 4. Back-office order search (order, PO or project number, customer or company name)

- API: `apps/api/src/orders/orders.service.ts:660 OrdersService.filters(search) via adminList()` (workload id `orders-admin-search`)
- Fix: `pg_trgm` GIN indexes and a rewrite of the OR across relations into a UNION
- Parameters: `pattern` = `%2024-0000%`

### Why it is slow

`ILIKE '%term%'` has a wildcard at the start, so no B-tree index can help: every order is read
and five patterns are tested on each. The customer-name and company-name conditions are
`IN (subquery)` inside the same OR, which forces a filter on each order row rather than an
index lookup. Adding indexes alone does not change that: as long as the OR mixes columns of
`orders` with conditions on other tables, the planner has to scan `orders`.

```sql
   OR o."userId" IN (SELECT u.id FROM users AS u WHERE u."fullName" ILIKE '%2024-0000%')
   OR o."organizationId" IN (SELECT g.id FROM organizations AS g WHERE g.name ILIKE '%2024-0000%')
ORDER BY o."createdAt" DESC
LIMIT 20 OFFSET 0
```

### Trade-off

Trigram GIN indexes answer `ILIKE '%term%'` by intersecting the posting lists of the term's
three-letter sequences; the matches are then rechecked against the real pattern. The rewrite
gives each condition its own branch: the order columns combine in a BitmapOr, and names are
looked up in `users` and `organizations` first and joined to their orders through the existing
foreign-key indexes. The result is the same set of orders.

Costs. Three GIN indexes on `orders` make every insert, and every update of those columns,
more expensive, and GIN indexes are large compared with the columns they cover (sizes in
`docs/indexing.md`). `fastupdate` (on by default) batches GIN insertions in a pending list,
which keeps inserts cheap but makes searches slower until autovacuum merges the list. Prisma
cannot express the UNION, so `OrdersService.filters()` would call `$queryRaw` for searches.
Terms shorter than three characters produce no trigrams and fall back to a scan; the API
should require at least three.

### Trade-off

of the key, so the sum is computed from the index alone (an index-only scan) as long as the
visibility map is current, which autovacuum maintains on an insert-mostly table. One index
serves three dashboard statements: this sum, the 30-day count (case 6) and the eight newest
orders (case 5). Prisma's `@@index` has no `INCLUDE`, so the index goes in a raw SQL migration
under Prisma's default name.

order, and it would serve the two 30-day statements with a bitmap heap scan. It cannot return
rows in order, though, so case 5 would still need a B-tree, and the BRIN would then be
redundant. A materialised view of daily totals would make the dashboard cheaper still, but it
answers "the last 30 calendar days as of the last refresh" rather than "the last 30 days", and
every refresh reads the whole table. With an index-only scan over one month of entries, a
materialised view is not justified at this scale.
